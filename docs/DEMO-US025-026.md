# Demo de correos de contingencia

Las US-025 y US-026 extienden la pantalla actual de Contingencias. El cambio de vuelo se guarda junto con una cola persistente en Supabase; la entrega SMTP se procesa después de responder. No se considera enviado un correo solamente por haber sido encolado.

## Preparación

1. Confirmar el proyecto Supabase de pruebas y aplicar las migraciones anteriores y `2026102902_flight_mail_outbox.sql`. No aplicar en otra instancia por inferencia. Esta entrega no ejecuta migraciones remotas automáticamente.
2. Iniciar la web con `DATA_PROVIDER=supabase`, `APP_SPRINT=3`, las variables Supabase habituales y una cuenta de administrador. SMTP debe apuntar a un servidor de pruebas, no a casillas reales.
3. Configurar `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` y `MAIL_FROM`. Opcionalmente definir `FLIGHT_SUPPORT_EMAIL` y `FLIGHT_SUPPORT_PHONE` para incluir canales específicos de atención. Sin ellos, el correo indica Mis reservas y el mostrador de SIGV.
4. Crear un vuelo futuro, preferentemente a más de 72 horas, con dos reservas confirmadas de contactos distintos y una reserva pendiente de pago. Una de las confirmadas debe contener dos pasajeros. Anotar códigos y contactos.
5. Abrir `/admin/contingencias`. El historial de correos aparece debajo de la lista de vuelos. La cuenta administradora es la única que puede consultar destinatarios e historial o procesar la cola desde la web.

En `DATA_PROVIDER=mock`, el formulario y la validación se pueden recorrer, pero no se guardan eventos ni se envían correos. Para demostrar persistencia, destinatarios y reintentos se necesita el proveedor Supabase de pruebas.

## US-025 Reprogramación automática

1. Buscar el vuelo y elegir **Reprogramar**.
2. Cambiar sus horarios y elegir **Revisar cambio**. Dejar el motivo vacío y confirmar.
3. Comprobar que la operación administrativa termina sin esperar una confirmación SMTP.
4. Pulsar **Actualizar** en Correos de contingencia y revisar las casillas del SMTP de pruebas.

**Resultado esperado:** una fila por reserva confirmada; ninguna para la pendiente. El correo contiene vuelo, reserva, ruta, nombres de los pasajeros, itinerario anterior y nuevo y vías de reprogramación/reembolso. La reserva de dos pasajeros recibe el aviso en su contacto registrado, con ambos nombres; no se inventan direcciones individuales de acompañantes. Si la llegada es anterior a la salida en el reloj, su fecha se muestra al día siguiente.

Repetir exactamente el mismo horario sin cambios efectivos no debe generar otro evento. Un cambio posterior real sí debe producir un evento independiente.

## US-025 Cancelación automática

1. Usar otro vuelo futuro con reservas confirmadas y una pendiente.
2. Elegir **Cancelar vuelo**, revisar el alcance y confirmar.
3. Consultar la cola, los correos y el estado de las reservas.

**Resultado esperado:** los contactos de las reservas que estaban confirmadas reciben el aviso explícito de cancelación, incluso cuando la política existente las mueve a A reagendar/A reembolsar. La captura de destinatarios ocurre antes de ese cambio, dentro de la misma transacción. La reserva pendiente no recibe un correo de pasaje confirmado. Los avisos internos y Auditoría continúan funcionando.

## US-025 Caída y recuperación de SMTP

1. En el entorno de pruebas, configurar temporalmente un SMTP inaccesible y reiniciar el servidor Next.js para descartar la conexión SMTP reutilizada.
2. Modificar un vuelo con reservas confirmadas.
3. Verificar que el vuelo se actualiza y que los correos quedan Pendiente/Reintento pendiente, con intento fallido e indicación del próximo intento.
4. Reiniciar la aplicación conservando la misma base. Comprobar que las filas siguen presentes.
5. Restaurar el SMTP de pruebas, reiniciar Next.js y esperar el próximo horario de reintento. Pulsar **Procesar pendientes** o ejecutar el programador configurado.

**Resultado esperado:** la operación de vuelo no se revierte por SMTP; el historial conserva la falla y el posterior envío. Los errores visibles no muestran contraseñas ni detalles internos del transporte. Dos procesadores concurrentes no toman la misma fila mientras su toma está vigente. Si una instancia muere, la toma vence a los cinco minutos y otra invocación puede recuperarla.

El sistema ofrece entrega con reintentos. Si SMTP recibió un correo pero la conexión se perdió antes de confirmar su resultado, un reintento podría duplicarlo: no se promete entrega exactamente una vez frente a una respuesta de transporte ambigua.

## US-026 Motivo opcional y literal

1. Reprogramar o cancelar otro vuelo y llegar a la confirmación.
2. Escribir en **Motivo de la contingencia**:

```text
Cuestiones climáticas
Revisión <operativa> & seguridad
```

3. Confirmar y revisar el cuerpo de texto y HTML del correo.
4. Repetir en otro evento dejando el motivo vacío.

**Resultado esperado:** se conservan el texto, los saltos y los caracteres visibles. El HTML se escapa y no se ejecuta. El campo vacío permite continuar; no reutiliza un motivo de una operación anterior. El límite de 2000 caracteres se informa y se valida también en la API.

## Programación y seguridad

El guardado de contingencias agenda una primera tanda mediante `after()` de Next.js. Cada tanda toma como máximo cinco correos. Para terminar colas grandes y ejecutar reintentos aunque no haya nuevas operaciones, se debe configurar una llamada periódica a:

```text
POST /api/internal/notifications/process
Authorization: Bearer <NOTIFICATION_PROCESSOR_SECRET>
```

`GET` admite el mismo contrato para programadores que lo requieran. Definir `NOTIFICATION_PROCESSOR_SECRET` y `SUPABASE_SERVICE_ROLE_KEY` únicamente del lado servidor. Nunca usar prefijo `NEXT_PUBLIC_` para esos valores. Configurar una invocación cada minuto en el programador del entorno; el despliegue de ese programador y la aplicación de migraciones requieren confirmar el destino.

Sin secreto o con secreto incorrecto, el endpoint responde 401. Sin proveedor persistente o configuración administrativa disponible, falla cerrado con 503. La web ofrece procesamiento manual mediante la sesión administradora, sin exponer la clave de servicio al navegador. Los usuarios pasajero/mostrador no pueden leer la cola ni ejecutarla.

Los reintentos comienzan aproximadamente al minuto y aumentan hasta una hora. **Procesar pendientes** respeta `next_attempt_at`: no fuerza filas cuyo horario todavía no llegó ni roba tomas activas.

## Comprobaciones locales automatizadas

```text
node --test tests/flight-change-mail.test.mjs tests/mail-outbox.test.mjs
npm test
npm run typecheck
npm run lint
npm run build
```

Las pruebas de plantillas/procesador usan transporte y almacenamiento de prueba; no envían correo real. Las garantías SQL de permisos, transacción, toma concurrente y recuperación requieren ejecutar la migración y los escenarios anteriores sobre una base de pruebas confirmada. No se deben presentar como validadas solamente por pasar pruebas de funciones TypeScript.
