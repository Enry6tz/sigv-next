# Demo de reportes y compra web responsive

Esta entrega extiende la aplicación Next.js + Supabase existente. No incluye PWA, aplicación nativa, push ni funcionamiento offline. Los pagos siguen siendo simulados.

## Preparación segura

1. Para una demo local sin datos reales, iniciar con `APP_SPRINT=3` y `DATA_PROVIDER=mock` en las variables del proceso, y ejecutar `npm run dev`.
2. Confirmar en `/api/health` que `provider` sea `mock` y `sprint` sea `3`. No ejecutar pruebas automáticas de mutación contra una base real.
3. Abrir `/api/data/flights` y tomar la fecha actual del vuelo `AR-1420` (se genera a siete días). La demo no usa una fecha fija.
4. Usar un ancho de pantalla de 390 px para la revisión móvil. Revisar también en un teléfono real antes de la aceptación final.

En modo mock los fixtures son explícitamente simulados. Las compras no persisten ventas reales ni modifican el fixture del reporte. Para verificar ventas nuevas de extremo a extremo se requiere una base Supabase de pruebas autorizada y sus migraciones aplicadas.

## US-027 Reporte de ocupación

1. Abrir `/admin/reportes` con rol administrador (la demo mock permite entrar sin credenciales reales).
2. Seleccionar vuelo `AR-1420`, clase `Economy` y su fecha en Desde/Hasta. Presionar **Aplicar**.
3. Esperado en el fixture: **2 pasajes vendidos**, **capacidad 86**, **ocupación 2.33 %**, **1 vuelo**. Pendientes y cancelados no se cuentan.
4. Descargar CSV. Debe contener la misma fila y los mismos valores; no debe incluir DNI ni filas de otros vuelos/clases.
5. Presionar **Limpiar**: reaparecen todos los vuelos y ambas clases, incluyendo filas con cero ventas.
6. Ingresar Desde posterior a Hasta y aplicar: aparece explicación y no se muestra tabla. Usar fechas sin vuelos: aparece mensaje sin resultados.

El indicador **Ocupación promedio** es la media aritmética de los porcentajes de las filas filtradas. Se muestra por separado la **ocupación global ponderada por capacidad** (vendidos totales / capacidad total). Los vuelos se cuentan una sola vez aunque aparezcan sus dos clases.

En Supabase, ejecutar además con un pasajero o mostrador: el recurso de reportes y su descarga deben rechazar el acceso; los DNI solo se entregan al administrador. No se modificaron los permisos para habilitar otros roles.

## US-028 Detalle de pasajes vendidos

1. Con el filtro anterior aplicado, hacer clic en la fila Economy de `AR-1420` (o activar su botón con teclado).
2. Esperado: panel con dos personas, **Lucía Fernández / 30123456** y **Tomás Prueba / 30123457**, ambas con reserva `SIGV-7K2P9`. Son datos ficticios.
3. Comprobar que la cantidad listada coincide con los **2 vendidos** del reporte.
4. Presionar **Volver al reporte**: se conservan los filtros y el foco vuelve al vuelo.
5. Abrir una fila sin ventas: aparece **No existen pasajes confirmados para este vuelo, fecha y clase**.

## US-029 Búsqueda desde el navegador móvil

1. A 390 px de ancho, abrir el buscador y elegir EZE → BRC, la fecha de `AR-1420`, solo ida y un pasajero.
2. Buscar, abrir **Elegir / Ver clases** y comprobar horarios, Economy, Primera y sus precios. No debe haber desplazamiento horizontal de toda la página.
3. Seleccionar una clase y continuar: se conserva vuelo, clase y cantidad de pasajeros.
4. Buscar la misma ruta en una fecha sin vuelos. Esperado: mensaje de disponibilidad y botón **Elegir fechas cercanas**.
5. Pulsar ese botón: se abre la edición de búsqueda y se enfoca la fecha, conservando ruta y cantidad. Los vuelos agotados no deben ofrecer una clase sin cupo para el grupo.

## US-030 Reserva y pago simulado desde el navegador móvil

1. Buscar `AR-1420` en Economy para **9 pasajeros**. Completar contacto y nueve nombres/documentos distintos válidos (6–8 dígitos).
2. Crear reserva y abrir el pago de prueba. La selección conserva los nueve pasajeros y el total.
3. Pagar con una tarjeta de formato válido para aprobación simulada. Esperado: **Resumen de Reserva**, confirmación y acceso a comprobantes. No se cobra dinero real.
4. Prueba negativa: repetir un DNI o borrar el correo. Debe impedir reservar y explicar el dato incorrecto.
5. Prueba de conexión: en una reserva de pruebas, bloquear la petición `/api/data/payments` desde las herramientas del navegador. Al pagar, aparece un aviso de conexión; el botón deja de estar bloqueado y los campos conservan sus valores. Una petición que no responde se aborta a los 15 segundos.
6. Recuperar conexión y usar **Verificar estado y reintentar**. Primero se consultan todos los tramos de la reserva: si ya están confirmados, se muestra el resumen sin otro POST de pago; si todos siguen pendientes, se permite reintentar; ante datos incompletos o falta de conexión, se bloquea el nuevo pago y se ofrece **Mis reservas**.

La comprobación automática de pérdida de respuesta del navegador simula un pago ya confirmado al recuperar la conexión y verifica que no se emita un segundo POST. La atomicidad real de inventario y pagos corresponde a las RPC de Supabase y debe verificarse en una base de pruebas; una demo mock sin persistencia no demuestra esa garantía.

## Verificación automática

- `npm test`: pruebas de helpers y, si no se define servidor, las pruebas HTTP se informan como omitidas.
- Con servidor mock activo: definir `PASSENGER_TEST_BASE_URL=http://127.0.0.1:3103` (o el puerto elegido) y ejecutar `npm test`; debe ejecutarse también `tests/passenger-flow.test.mjs` sin omisiones.
- `npm run typecheck`, `npm run lint`, `npm run build` con `APP_SPRINT=3`, `DATA_PROVIDER=mock`.

No se necesitan migraciones nuevas para estos reportes: se consultan las tablas existentes de vuelos, reservas y pasajeros, conservando la autorización del servidor y paginando para no truncar los totales por el límite de la Data API.
