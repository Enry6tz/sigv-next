# Demo de estados cupos y pagos simulados

Esta entrega extiende la aplicación web Next.js + Supabase. No procesa dinero real, no crea una PWA y no implementa funcionalidades offline.

## Preparación

1. Aplicar las migraciones base existentes y luego `supabase/migrations/2026102901_flight_policy_inventory_payments.sql` en una base **de prueba**.
2. Usar cuentas de prueba de pasajero, administrador y mostrador. Crear vuelos con fecha futura a más de 48 horas, 10 cupos Economy y 2 Primera. Mantener también un vuelo dentro de las próximas 48 horas.
3. Iniciar la web con `APP_SPRINT=3`. Para persistencia real de pruebas, usar el Supabase de prueba. `DATA_PROVIDER=mock` solo devuelve simulaciones y no demuestra persistencia ni concurrencia.
4. Tarjeta aprobada: `4111 1111 1111 1111`. Tarjeta rechazada: `4000 0000 0000 0002`. Titular: `Demo Passenger`; vencimiento: `12/99`; CVV: `123`. Usar únicamente datos sintéticos.

## US-033 Política operativa

| Paso | Acción | Resultado esperado |
| --- | --- | --- |
| 1 | Confirmar una reserva y hacer check-in de un pasajero desde Mostrador. Anotar asiento y datos de check-in. | El pasaje tiene asiento asignado y reserva confirmada. |
| 2 | En Administración → Contingencias, elegir “Cambiar fecha u horario”, demorar una salida de 10:00 a 11:00 y revisar/confirmar. | Estado Retrasado, salida vigente 11:00. Conserva asiento y check-in. |
| 3 | Repetir con salida 11:30. | Salida 11:30, no 12:30. La hora absoluta reemplaza a la anterior. |
| 4 | Adelantar a 10:30 y luego a 09:30, en la misma fecha. | 10:30 sigue Retrasado respecto de la programada 10:00; 09:30 queda Activo. |
| 5 | Cambiar la fecha del vuelo cercano, dentro de las próximas 48 horas. | Rechazo que explica el límite; no cambia la fila. |
| 6 | Repetir el cambio de fecha con el vuelo lejano. | Se permite, conservando los pasajeros/asientos/check-in. |
| 7 | Intentar editar un vuelo Cancelado, Reprogramado u Operado. | No ofrece controles operativos y la API/DB rechaza indicando el estado terminal. |
| 8 | Preparar un vuelo local con salida vigente vencida hace más de dos horas, sin despegue. Consultar Contingencias. | Estado Operado; no admite cambios ni nuevas ventas. |

El cierre se materializa al consultar Contingencias. La migración configura además un trabajo cada minuto **solo si `pg_cron` ya estaba instalado**. Si no está disponible, un administrador debe configurar la ejecución periódica de `select public.sigv_close_due_flights()`; no se afirma que exista un planificador externo instalado.

### Precisión pendiente del criterio 2

El documento dice “anterior o igual a la salida vigente (+2 h si no despegó)”, pero no define con claridad si limita el momento de registrar la demora o la nueva hora propuesta. Se implementa la ventana operativa hasta dos horas después de la salida vigente y el reemplazo de horario; **no se inventa un máximo adicional para la nueva hora**. Tampoco se convierte automáticamente todo cambio de fecha en estado terminal Reprogramado sin confirmar esa regla de negocio.

## US-034 Cupos vendidos y asientos físicos

| Paso | Acción | Resultado esperado |
| --- | --- | --- |
| 1 | Abrir Administración → Capacidades y seleccionar el vuelo de prueba. | Grilla por clase con capacidad, vendidos, disponibles y asientos asignados; total vendido visible. |
| 2 | Crear reserva de dos pasajeros sin pagar. | No consume cupos: las reservas pendientes no son ventas ni retenciones. |
| 3 | Aprobar el pago simulado. | Vendidos Economy +2, disponibles −2, asignados sin cambios. |
| 4 | Consultar Mostrador → Manifiesto o Asientos. | Mismo desglose comercial; los asientos siguen libres hasta el check-in. |
| 5 | Hacer check-in de un pasajero. | Asignados +1; vendidos no cambia. |
| 6 | En otra reserva confirmada sin check-in, cancelar desde Mis reservas. | Cupos restituidos una vez y vendidos decrementados. |
| 7 | Desde una sesión administradora, ejecutar el reembolso simulado con `PATCH /api/data/payments`, cuerpo `{"action":"refund","reservationCode":"CODIGO_DE_PRUEBA"}`. | Reserva Cancelada, pago Reembolsado (simulado), cupo liberado una vez. La factura histórica no se borra. Repetir se rechaza. |

La cancelación conserva la regla preexistente: una reserva con check-in no se cancela mediante este flujo. No se agrega una pasarela de reembolsos reales.

### Prueba concurrente real

1. En la base local descartable, preparar un vuelo con **un** cupo Primera y dos reservas pendientes de un pasajero con documentos diferentes.
2. Usar dos sesiones SQL o dos sesiones de usuario distintas para ejecutar `sigv_simulated_checkout` a la vez sobre esas reservas.
3. Esperar una aprobación y un rechazo “No hay suficientes asientos Primera”; vendidos Primera = 1 y disponibles = 0. El perdedor sigue pendiente, sin pago/factura.
4. Repetir con un vuelo que tenga **dos** cupos Primera: las dos compras de un pasaje deben aprobarse, vendidos = 2 y disponibles = 0.

El texto original menciona dos cupos pero espera un solo ganador sobre “el último cupo”. Se separan ambos escenarios para no introducir una restricción de venta incorrecta.

## US-035 Rechazo determinista

1. Crear una reserva de prueba y anotar cupos disponibles y total vendido.
2. Abrir el pago e ingresar `4000 0000 0000 0002`, titular, vencimiento y CVV válidos.
3. Confirmar. Debe mostrarse **pago rechazado por el simulador**, no un error de formato. La API responde HTTP 402 con `PAYMENT_DECLINED` y estado `RECHAZADO`.
4. Revisar Mis reservas: permanece Pendiente de pago. No hay e-ticket, factura ni correo nuevo, ni cambios de cupos.
5. Repetir: mismo rechazo y ningún consumo adicional.
6. Cambiar únicamente el número por `4111 1111 1111 1111` y pagar. Se confirma una sola vez y descuenta exactamente el grupo.
7. Reintentar la misma aprobación mediante la API: devuelve la factura existente con `replayed:true`; no crea otra venta ni reenvía comprobantes desde ese reintento.

## Verificación automatizada

```powershell
$env:DATA_PROVIDER='mock'; $env:APP_SPRINT='3'
npm run dev -- --hostname 127.0.0.1 --port 3101
# En otra terminal:
$env:PASSENGER_TEST_BASE_URL='http://127.0.0.1:3101'
npm test
npm run typecheck
npm run lint
npm run build
```

Para base local: `psql -v ON_ERROR_STOP=1 -f tests/core-policies.integration.sql`. El script utiliza usuarios sintéticos, exige el esquema base y revierte sus fixtures con ROLLBACK. Comprueba terminales, 48 h, demoras, conservación de check-in, rechazo sin pago, repetición de aprobación, devolución y agotamiento secuencial. **La prueba de concurrencia de dos conexiones es adicional, no queda demostrada por una prueba secuencial.**
